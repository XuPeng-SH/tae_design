# 一天涌入 40+ 个 PR：AI 时代的数据库内核如何持续可发布？

> MatrixOne 用 Agent 运筹变更风险、测试组合与多云资源，支撑 main 高速迭代和每两周 release 分支

七月的一天，我们有 40 多个 PR 进入研发流程。

这一天像一个快进镜头：需求在变化，代码在生成，Review、CI 和测试任务不断进入队列。与此同时，我们还保持着另一个节奏——main 持续快速迭代，每两周从 main 拉出一个 release 分支，准备版本发布。

这构成了一个越来越普遍的研发难题：

> 代码进入 main 的速度越来越快，怎样让发布信心以同样的速度增长？

如果发版前冻结 main，快速迭代会被周期性打断；如果不冻结，却把质量问题留到 release 分支再集中处理，发版就会陷入回归、修复、回合入和重新验证。代码写得更快了，版本反而未必发得更快。

这是 MatrixOne 内核开发遇到的真实问题。一个版本周期内，SQL Parser、优化器、执行器、事务、锁、存储、S3、缓存和分布式服务都可能持续变化。代码生产越来越便宜，但证明这些变化没有破坏语义、一致性、恢复能力和性能，仍然昂贵。

我们的应对方式，是把 Quality Engineering 从一套测试流程，升级成一套由 Agent 参与运筹的质量控制系统。

它持续回答五个问题：

1. 这次变化可能破坏什么？
2. 我们已经掌握了哪些可信证据？
3. 还缺哪些验证才能安全合入和发布？
4. 有限的测试环境和时间应该投到哪里？
5. 这次结果如何让下一轮计划变得更好？

Agent 带来的重要变化，不是多生成几个 Case，而是让这些高频、复杂的质量决策开始具备规模化能力。

如果只记住这套实践的核心转变，可以看下面这张表：

| 固定流水线主要关注 | Agent 运筹进一步关注 |
| --- | --- |
| 从固定测试清单出发 | 从当前变更的证据缺口出发 |
| PR 尽量跑同一套流程 | 高风险变更获得更多、更有针对性的验证 |
| 环境由人申请和协调 | 环境被描述成能力，由调度器动态分配 |
| CI 只给出通过或失败 | 每次执行形成有范围、有来源、有时效的质量证据 |
| release 分支重新汇总质量状态 | main 持续积累证据，release 验证版本级风险和失效证据 |
| 人工在队列、日志和群消息间协调 | Agent 处理高频决策，人负责质量底线和重大风险 |

## 一、AI 加速代码之后，验证成为新的瓶颈

AI 很擅长完成局部任务：补一个接口、重构一段逻辑、生成单元测试、根据错误日志给出修复。但复杂系统真正难的地方，往往没有完整写在任务描述里。

在数据库内核中，一次看似局部的修改可能沿着执行路径继续扩散：

- Parser 或 Binder 的修改可能改变 SQL 兼容性和语义边界；
- 优化器规则可能生成合法但代价更高，甚至语义不等价的执行计划；
- 执行器修改可能破坏批次协议、取消传播和资源释放；
- 事务与锁修改可能只在特定并发历史下暴露一致性问题；
- 存储、S3 和磁盘缓存修改可能改变数据正确性与尾延迟；
- 日志、恢复和分布式服务修改可能只在节点异常时暴露问题。

AI 生成的代码可能编译成功，生成的测试也可能全部通过，但这只能说明它通过了已经执行的检查，不能说明真正的风险都被覆盖了。

这就像一张只写着“正常”的体检报告：如果不知道检查了哪些项目、使用了什么样本、报告是什么时候产生的，“正常”本身并不足以支持判断。

Vibe Coding 因此改变了研发系统的约束。团队首先被压垮的往往不是写代码，而是理解变化、选择测试、协调环境和分析失败。人工经验可以处理一天几个关键变更，却很难稳定处理突然涌入的几十个 PR。

所以，质量工程需要解决的已经不只是“如何自动执行测试”，还包括“如何自动形成合理的测试决策”。

## 二、先换一个问题：我们还缺什么质量证据？

传统 CI 通常从测试清单出发：某类 PR 触发哪些 Job，Job 全绿就允许合入。

我们的思路从另一个方向开始：一次变更需要哪些证据，当前已经有哪些证据，两者之间还差什么？

    当前变更要求的质量证据
              -
    已经存在且仍然有效的证据
              =
           证据缺口

这个“证据缺口”是动态测试计划的起点。

质量证据也不只是一个通过或失败状态。至少要包含：

    Evidence {
        subject:    代码与 image 版本
        scope:      覆盖的模块、场景和风险
        context:    环境、配置和数据集
        oracle:     判断正确性的标准
        result:     结果、日志和指标
        validity:   产生时间与失效条件
    }

说得直白一些，一份证据必须回答：测的是哪份代码，测了什么，在哪里测，凭什么判定正确，以及什么时候需要重测。

这最后一点非常重要。质量证据不是永久有效的。

一个 PR 改变了同一条调用链，原来的功能结果可能失效；一个 image 更新了底层依赖，原来的兼容性结论可能需要重验；一个性能优化改变了缓存策略，原有 P99 基线也可能不再适用。

因此，main 的发布信心不能只是一个不断累加的分数。它更像一组持续更新的证据：新变化会增加证据，也可能让旧证据过期。

Agent 的任务，就是理解这种变化，计算当前证据缺口。

证据本身也有生命周期：

    Missing ──调度──→ Running ──通过──→ Valid
                         │                  │
                         ├──测试失败──→ Failed
                         └──环境/超时──→ Inconclusive

    Valid ──受影响的变化──→ Stale ──重新调度──→ Running
    Inconclusive ──────────重新调度────────────→ Running

环境不可用、任务超时或者日志缺失，都不能被解释成“没有发现问题”，它们只能得到 Inconclusive。只有把 Missing、Running、Valid、Failed、Stale 和 Inconclusive 分开管理，发布判断才不会被一个模糊的绿色状态误导。

## 三、Agent 更像质量塔台，而不是测试机器人

我们没有把所有工作交给一个“万能 Agent”，而是把质量过程拆成一条可解释的控制闭环：

    代码 Diff、依赖、Issue、CI、线上反馈
                         ↓
                  变更影响与风险画像
                         ↓
                    质量证据缺口
                         ↓
                 测试组合与资源计划
                         ↓
          dev / QA / 公有云 / 私有 Cloud
                         ↓
                 失败归因与质量判断
                         ↓
             更新 Case、规则和下一轮计划

Agent 在这里更像一个塔台。

塔台不负责驾驶每架飞机，但要知道哪项任务最紧急、需要哪条跑道、哪些任务可以并行、哪些任务必须等待，以及出现异常后如何重新调度。

在质量系统中，Agent 分别承担几类判断：

- 变更分析：从 Git Diff 继续追踪 Parser、Planner、Executor、Transaction、Storage 等内核路径及历史问题；
- 风险建模：判断影响范围、失败后果、暴露条件和可检测性；
- 测试计划：将风险转成证据要求，再选择 Case 和数据集；
- 资源调度：为任务匹配环境、容量和执行优先级；
- 失败归因：区分代码缺陷、环境异常、Case 问题和 Flaky（同一代码下偶发成功或失败）；
- 反馈学习：根据新缺陷和测试结果更新后续计划。

风险画像至少包括影响范围、失败后果、触发条件、新颖程度和可检测性。影响图也不能只依赖静态函数调用，还需要结合模块依赖、配置与数据路径、运行时 Trace、代码 Owner 和历史 Issue。对于新模块或缺少历史数据的路径，系统不能因为“过去没有失败”就判为低风险，而应把不确定性本身计入风险，扩大验证或者升级人工评审。

这个过程有一个关键顺序：先定义风险和证据要求，再选择测试。

如果直接让 Agent 从几千个 Case 中根据名称“猜应该跑什么”，它很容易停留在表面相似度。一个修改 reader 的 PR，可能真正影响的是缓存逐出、网络重试和资源关闭；这些关系未必能从 Case 名称中看出来。

只有先建立变更影响图，再计算证据缺口，测试选择才有稳定依据。

落到实现上，计划生成可以抽象为一组清晰的数据契约：

    profile       = Analyze(change, dependencyGraph, issueHistory)
    requirements  = ApplyPolicy(profile, qualityGuardrails)
    validEvidence = ResolveEvidence(headCommit, impactGraph, requirements)
    gaps           = requirements - validEvidence
    plan           = Optimize(gaps, testCatalog, resourceState)
    decision       = ExplainAndGate(plan, confidence, policy)

这段流程里，Analyze 可以使用大模型理解变更意图、关联历史 Issue 和提出风险假设；ApplyPolicy、ResolveEvidence 和 Gate 则更适合由确定性逻辑实现。Agent 输出的是结构化风险、证据要求和计划，而不是一段难以执行和审计的自然语言建议。

## 四、有限资源下，测试计划是一个运筹问题

围绕 MatrixOne 内核，我们已经积累了不少测试资源：

- 阿里云和腾讯云上的固定 VM、S3；
- 长期运行并每天更新 image 的 dev、QA 环境；
- 上海 IDC 的私有 Cloud；
- 大量 SQL 语义、优化器、执行器、事务并发、存储恢复、性能和历史回归 Case；
- 多种规模和分布的数据集。

如果这些资源仍然各自排队、各自执行，它们只是一份环境清单。Agent 要进行运筹，首先需要把它们变成一个统一的“能力资源池”。

dev 的特点是接近最新 main、反馈快；QA 适合更大范围回归、跨模块组合和长时间运行；阿里云、腾讯云提供真实的多云 VM、S3 和网络条件；IDC 私有 Cloud 覆盖私有化部署和基础设施差异。

测试任务声明自己需要什么能力，而不是直接指定某台机器。调度 Agent 再根据环境健康、当前 image、资源配额、排队时间和任务优先级选择执行位置。

测试 Case 同样需要被量化。一个 Case 的价值至少取决于：

- 与当前风险的相关性；
- 历史上发现缺陷的能力；
- 相对其他 Case 的覆盖独特性；
- 执行稳定性；
- 时间、机器和环境成本。

测试计划可以抽象成一个带硬约束的多目标优化问题：

    优先提高：
    风险覆盖、缺陷发现收益、覆盖独特性和证据时效

    同时降低：
    执行时间、资源成本、重复覆盖和 Flaky 噪声

    约束：
    质量护栏、反馈时限、资源容量和必要环境覆盖

SQL 结果正确性、事务一致性、存储数据完整性和关键兼容性属于硬约束。Agent 不能因为资源紧张或者历史失败率低而静默跳过。资源预算内如何组合更多高价值测试，才是动态优化空间。

实际求解分两层：先根据硬约束生成所有合格计划，再在合格计划中比较反馈时延、资源成本和风险收益。这样可以避免用一个看似精确的综合分数，让低成本测试“抵消”必须覆盖的高损失风险。

我们刻意把“适合概率判断的工作”和“必须确定执行的工作”分开：

| 更适合 Agent 辅助判断 | 更适合确定性系统控制 |
| --- | --- |
| 理解 PR 意图和潜在跨模块影响 | 必须执行的质量护栏 |
| 检索相似 Issue 和历史缺陷 | 证据有效期和失效规则 |
| 推荐风险相关 Case 和数据集 | 资源配额、超时和抢占约束 |
| 聚类日志、生成失败假设 | 合入与发布门禁 |
| 发现测试覆盖空洞 | 审计、回放和回滚 |

这样的分工降低了两个风险：既不会把 Agent 限制成只会搜索 Case 的助手，也不会让一个概率模型直接掌握不可逆的发布权力。

具体调度中，我们区分两类任务：

- PR 快速通道：尽快给开发者提供第一份可信反馈；
- main 持续验证：补充跨模块、长周期、多云和真实部署证据。

资源高峰时，调度器可以合并相同版本、相同上下文的重复任务，为高风险修改预留或抢占资源，把长周期测试放到 QA 后台运行。只有当旧任务不再服务任何候选 commit、release 分支或失败诊断时，才允许取消。release 分支也需要独立预算，避免发版验证被 main 的并发流量淹没。

机器利用率并不是越高越好。所有资源持续 100% 占用，就像机场所有跑道永远排满：一旦真正高风险的任务到来，系统反而没有响应能力。

## 五、看一个内核实例：S3 读取路径发生变化

假设一个 PR 修改了 S3 reader 或磁盘缓存逻辑。

S3 是远端对象存储，磁盘缓存则把一部分远端数据保留在本地，以减少重复访问。代码 Diff 可能只有几十行，但它背后的风险远不止“能不能读到文件”：

- range read 返回的数据是否仍然正确；
- 缓存命中、未命中和逐出后是否一致；
- 网络错误和重试是否重复消费 reader；
- 并发读取是否产生资源竞争或泄漏；
- S3、缓存和 reader 各阶段的 P99 是否退化。

变更分析 Agent 沿数据路径和调用关系展开影响面，并结合历史 Issue 形成风险画像。测试计划 Agent 再把风险翻译成证据要求。

PR 阶段先跑基础读写、错误路径和资源关闭等快速护栏；缓存逐出、并发和重试进入针对性计划；阿里云、腾讯云的 S3 环境验证真实对象存储行为；QA 承担大数据量、P99 和长时间运行；如果涉及私有化对象存储适配，再进入 IDC 环境。

假设 QA 发现 read-disk-cache P99 变慢，而 get-reader 仍然正常。系统不能只报一句“性能回归”，还要关联缓存命中率、磁盘队列、文件大小分布、逐出行为、并发量以及同时段的 S3 指标，判断问题更可能来自磁盘读取、缓存抖动、资源竞争还是指标口径。

修复提交后，Agent 重新计算影响范围。与修改无关、仍然新鲜的证据可以保留；缓存、并发和性能相关证据则被标记为失效并重跑。

最终留存的不是一串孤立的 CI Job，而是一份清晰的结论：这个变更引入了哪些风险，哪些风险已经被什么证据关闭，还有哪些需要在 main 的持续验证中继续观察。

这份证据随后跟随代码进入 main，也成为两周后 release 判断的一部分。

同一套方法也适用于其他内核路径。

例如，Planner 新增一条表达式改写规则，风险不只是“计划能不能生成”，还包括 NULL 语义、聚合与非聚合边界、别名可见性、MySQL 兼容性以及计划变化后的性能。对应证据可能来自定向语义 Case、与 MySQL 的差分结果、随机 SQL、计划不变量和典型数据集上的执行指标。

事务与锁路径则需要另一种证据。一个单线程测试很难证明并发正确，系统需要构造不同事务历史，覆盖等待、取消、死锁、重试和节点重启，并检查提交顺序、可见性和资源释放等不变量。

Agent 运筹的通用性正在这里：它不会把所有内核修改塞进同一条流水线，而是根据 Planner、Executor、Transaction、Storage 等不同路径，生成不同的风险模型和验证策略。

## 六、让 main 持续获得发布资格，release 才能真正快

很多团队把 release 当成一次期末考试：平时快速开发，拉分支后再集中确认质量。问题是，变化越多，考前突击越不可控。

我们的做法，是把发布验证拆到此前两周中的每一天。

PR 阶段解决直接风险和反馈速度；合入 main 后，dev、QA、多云和 IDC 继续补充更广、更深、更长时间的证据；新的 PR 会主动失效已经过期的结论；Issue、历史缺陷和线上反馈则持续改变风险规则和测试优先级。

main 因此不是一个只负责接收内核代码的分支，而是持续接受“发布资格审查”的主干。准备度始终绑定到具体候选 commit：一个新的高风险 PR 合入后，准备度可能立即下降，直到新增证据缺口被关闭。

发布准备度也不是一个总通过率，而是一组不能互相抵消的维度：

    Release Readiness = {
        correctness,    // SQL 结果与数据正确性
        consistency,    // 事务、并发与存储不变量
        compatibility,  // SQL、协议、升级与版本兼容
        resilience,     // 故障、恢复和长时间运行
        performance,    // 吞吐、延迟、资源消耗与回归
        operability     // 部署、诊断和问题恢复能力
    }

功能测试全部通过，不能抵消一个明确的事务一致性风险；平均延迟改善，也不能掩盖严重的 P99 回归。每个维度都需要达到自己的门槛，这比把几万个测试压缩成一个“通过率 99%”更接近真实发布判断。

每两周准备拉 release 分支时，系统先回答一组 Readiness 问题：

- 所有高风险变更是否已经补齐证据；
- 关键证据是否仍然有效；
- 是否存在未解释的严重回归；
- SQL 语义、事务一致性和存储恢复护栏是否完整；
- 目标云和私有化环境是否覆盖；
- 性能、稳定性是否偏离基线；
- 最近的修复是否已经正确进入 main。

满足这些条件后，release 分支重点验证版本特有的内容：升级与恢复、安装交付、兼容性、完整性能基线、已知问题和分支后的增量修改。

release 不需要盲目重复 main 上所有仍被证明有效的验证，也不能继承 main 中尚未解释的风险。版本级强制验收始终执行；只有能够通过影响关系、环境指纹和有效期证明仍然成立的证据才能复用。release 因此从“集中发现基础问题的战场”，变成对过去两周质量积累的最后确认。

release 上发现的问题也必须回到闭环中：代码修复同步到 main，缺失场景转化为 Case，错误的测试选择修正风险模型和调度规则。否则，我们只修复了当前版本，没有提升下一次发布能力。

这套机制带来一个关键认识：

> 发布不是某一天发生的事件，而是 main 每天持续保持的一种能力。

## 七、测试计划必须会进化，而不是越积越厚

Vibe Coding 同样可以快速生成大量测试。如果只看 Case 数量和代码覆盖率，测试资产会迅速膨胀，却不一定更能发现问题。

我们为 Case 建立多维画像：SQL 特性、内核模块、调用路径、事务历史、失败模式、数据规模、并发条件、部署环境、历史发现、执行成本和 Flaky 情况。它们共同形成一张覆盖矩阵。

测试资产治理主要关注三个问题。

第一，强度。一个 Case 的断言是否真的能识别错误？SQL 语义可以通过差分测试和 Metamorphic Test（改变输入后检查结果是否仍满足应有关系）验证，事务可以通过受控并发历史检查不变量，存储与恢复可以通过故障注入验证，通用逻辑还可以使用 Mutation Test（主动制造小错误，检查测试能否抓住）和历史缺陷回放。一个永远不会失败的测试，也可能只是没有能力发现错误。

第二，正交性。多个昂贵 Case 如果长期覆盖同一风险，却没有提供独特信息，就应该合并、降频或者重新设计。资源应该留给新的风险维度。

第三，适应性。出现严重 Issue 后，不能只补一个回归 Case，还要做 Test Gap Analysis（测试缺口分析）：之前为什么没有发现？是缺少场景、数据、环境和故障模型，还是已有 Case 没有被选中？答案必须改变下一轮风险模型、测试计划或质量门禁。

动态计划上线前还需要经过 Shadow Mode，也就是“影子验证”：Agent 先给出自己会选择哪些测试，但暂时不控制真实门禁，后台继续与原有计划或全量测试对照。

我们关注它漏掉了哪些失败、增加了哪些无效执行，以及对高风险场景的召回率。只有经过足够对照，Agent 才逐步获得真实决策权。

这保证了测试优化不是“为了少跑而少跑”，而是在可验证的前提下，用更低成本保持甚至提高缺陷发现能力。

## 八、Agent 可以运筹，但不能成为质量黑箱

Agent 会犯错：它可能低估影响范围，被不完整的历史数据误导，或者为了缩短反馈时间给出过于激进的计划。

因此，质量系统还需要一个独立于模型的治理面：

- 确定性规则定义不可绕过的质量护栏；
- 证据不足或者模型低置信度时默认升级验证；
- 每次计划都能解释覆盖了什么、跳过了什么；
- 输入、规则、环境、执行和结果全程可审计；
- 高风险豁免和最终发布有明确责任人；
- Agent 版本和策略可以回放、对照与回滚。

人的角色也会随之变化。

开发者需要说明变更意图和潜在影响；测试人员从重复执行转向风险建模、场景设计和测试资产治理；技术负责人制定质量底线、资源策略和发布标准；Agent 负责高频的信息处理、组合优化和执行协调。

Agent 不是质量责任的替代者。它的价值，是让质量责任在变化量突然放大时仍然能够被有效履行。

评价这套体系，也不能只看跑了多少 Case 或机器利用率多高。至少需要同时观察：

| 维度 | 核心指标 | 要回答的问题 |
| --- | --- | --- |
| 质量 | SQL 差分错误、事务异常、存储/恢复缺陷、高严重性缺陷逃逸 | 内核错误是否被更早、更有效地发现 |
| 反馈 | PR 首次可信反馈时间、P95（95% 的 PR 获得反馈所需时间）、失败归因时间 | 开发者是否真的更快得到结论 |
| 发布 | main 健康度、release 稳定周期、紧急修复数量 | 高速迭代是否转化成可预测发布 |
| 资源 | 单位风险覆盖成本、排队时间、重复执行比例 | 有限资源是否投入高价值验证 |
| Case | Flaky、覆盖独特性、历史缺陷检出能力 | 测试资产是否有效、稳定、正交 |
| Agent | 高风险召回、Shadow 漏检、人工推翻率 | Agent 的决策是否可信并持续改善 |

这些指标必须联合判断。反馈变快但严重缺陷逃逸增加，不是成功；资源成本下降但高风险召回下降，也不是成功；Agent 自动化率提高但没人能解释其决策，同样不是成功。

## 九、落地顺序：先建立事实，再逐步交给 Agent 决策

回头看，这套系统不能从一个“全自动质量 Agent”开始。Agent 能力建立在结构化事实之上，我们采用的落地顺序分为四步。

第一步，统一质量数据。

先把 commit、image、环境、配置、数据集、Case、结果、日志指标和 Issue 关联起来。最小的数据关系可以表达为：

    Change → Risk → Evidence Requirement → Test Plan
                                          ↓
    Resource → Test Run → Evidence → Issue / Release Readiness

这一步没有复杂智能，却决定后续结论是否可解释、可复现。数据仍然散落在 CI、日志、表格和人的记忆里时，Agent 只能生成看起来合理的建议。

第二步，用规则建立第一版风险和护栏。

从最熟悉的内核路径开始，例如 Planner、Transaction 或 Storage。由模块 Owner 定义关键不变量、历史高风险场景、必须执行的测试和环境要求。Agent 先负责收集信息、生成风险画像和解释推荐，不直接改变门禁。

第三步，在 Shadow Mode 中验证测试选择和资源调度。

将 Agent 计划与原有计划并行对照，观察高风险召回、漏检、反馈时间和资源成本。确定哪些判断可以自动执行，哪些仍需确定性规则或人工确认。资源调度也从低风险任务开始，逐步引入合并、抢占、配额和独立 release 预算。

第四步，打通问题反馈和 release Readiness。

让测试失败、线上 Issue 和 release 缺陷自动进入 Test Gap Analysis，更新 Case、风险规则和证据要求。到这一步，Agent 才不只是一次性生成计划，而是能够从结果中持续校准下一轮决策。

每一步都应该产生独立价值：即使暂时没有自动测试选择，统一证据和环境上下文也能改善失败复现；即使 Agent 尚未控制门禁，风险画像和失败归因也能减少人工协调。这样可以避免把整个体系押在一个大而全的 Agent 上。

## 结语：AI 让代码生产规模化，Agent 要让质量决策规模化

七月那一天的 40 多个 PR，只是研发变化加速的一个缩影。

真正的问题不是团队能不能生产更多代码，而是质量体系能不能同样快速地理解变化、选择验证、调度资源并形成可信结论。

我们在 MatrixOne 内核研发中建设的 Quality Engineering，最终是一套由 Agent 参与运筹的质量控制系统：它连接内核代码、Issue、历史缺陷、Case、数据集、环境资源和发布政策，持续计算风险与证据缺口，在有限资源下选择最有价值的验证，再从每次执行和问题中修正下一轮决策。

这套方法首先服务于数据库内核，也提供了一些可以复用的工程认识：

- AI 编程首先提高的是代码供给，研发体系必须同步提高验证和决策能力；
- 快速发布依赖 main 持续积累可信证据，而不是发版前集中冲刺；
- 测试优化的目标是单位资源的风险发现价值，而不是测试数量；
- Agent 最适合承担高频的信息处理和组合决策，质量底线与责任仍由明确规则和人掌握。

当质量决策能够规模化，高速迭代与快速发布才不再彼此牺牲。

每两周能够稳定拉出 release 分支、并让版本快速进入发布准备，基础并不是 release 阶段跑得更快，而是此前每一次变化，都获得了与风险相匹配、可以解释、可以复现的验证。
