# 当 Agent 开始运筹质量：MatrixOne 如何让高速迭代与两周一发同时成立

七月的一天，MatrixOne 有 40 多个 PR 进入研发流程。

它是一个缩影：Vibe Coding 正在显著降低代码生产成本。需求拆解、代码实现、测试生成和问题修复都在加速，main 上的变化越来越密集。与此同时，我们仍然保持每两周从 main 拉出 release 分支、准备版本发布的节奏。

对不熟悉研发流程的读者，可以把 main 理解为所有日常修改持续汇入的主干；release 分支则像每两周从主干取出的一个版本快照，它需要经过最后确认后交付给用户。

这两件事放在一起，构成了研发质量的新矛盾。

main 变化越快，两周内需要理解和验证的内容越多；release 想发得越快，留给集中回归、定位和修复的时间越少。如果依赖发版前冻结 main，高速迭代就会被周期性打断；如果继续快速合入，却等到 release 分支再集中发现问题，发布就会变成反复修复、回合入和重新验证。

如果把发版看成一场期末考试，这种模式等于平时只顾赶进度，最后几天才开始确认所有知识点是否掌握。功能越多、变化越快，考前突击越不可控。我们需要做的，是把发布验证拆到每一次日常变化中。

传统测试体系通常靠增加 Case、延长回归或增加机器来缓解压力。但在 Vibe Coding 场景下，增长最快的是变化本身。固定测试计划很快会遇到两个极端：要么每个 PR 都跑大量测试，反馈越来越慢；要么为了速度缩减验证，把风险推迟到 main 或 release。

所以我们重新定义了 Quality Engineering 的目标：

> 不追求每次执行最多的测试，而是在质量底线之上，让 Agent 持续识别风险、计算证据缺口、组合测试并调度资源，使 main 在高速变化中持续积累可发布信心。

这是从“测试自动化”到“质量运筹”的变化。自动化解决如何执行，运筹解决此刻最应该验证什么、把资源投到哪里，以及如何从结果中修正下一次决策。

## 一、Vibe Coding 改变了研发系统的瓶颈

AI 可以快速生成一段看起来合理的实现，也可以生成配套单元测试，但数据库系统中真正困难的部分往往没有直接写在需求里：

- 一个局部修改是否破坏了跨模块不变量；
- 并发、重试和异常路径是否仍然正确；
- 资源是否在取消、失败和提前返回时得到释放；
- S3、缓存和网络组合是否改变尾延迟；
- 小数据上的正确结果能否扩展到真实数据规模；
- 新测试是否拥有有效断言，而不只是覆盖了代码行。

代码生产变快以后，人工 Review、测试选择、环境协调和失败归因会先成为瓶颈。真正稀缺的从“谁来写代码”转向了三种能力：

第一，及时理解一次变化的真实影响；第二，为风险选择足够而不过量的验证；第三，在有限环境和时间内尽快形成可信结论。

因此，Quality Engineering 不能只是测试团队的效率工程。它必须成为连接开发、测试、CI、环境、Issue、线上反馈和发布决策的研发控制系统。

## 二、发布信心不是一个绿灯，而是一组有边界、有来源、有时效的证据

CI 全绿容易给人一种确定感，但绿色本身并不能说明覆盖了什么，也不能说明结论对后续代码是否仍然有效。

这就像一张只写着“正常”、却没有检查项目、样本和时间的体检报告。它看起来令人安心，却不足以支持真正的判断。

我们把“质量证据”定义为一个结构化对象：

    Evidence {
        subject:    commit / image
        scope:      覆盖的模块、场景和风险
        context:    环境、配置、数据集和依赖版本
        oracle:     如何判断正确或失败
        result:     结果、日志、指标和产物
        freshness:  产生时间以及有效条件
        provenance: 测试计划和决策依据
    }

说得直白一些，一份质量证据必须回答五个问题：测的是哪份代码，测了什么，在哪里测，凭什么判定正确，以及这个结论在什么情况下会失效。

这一定义解决了三个问题。

首先是可解释。我们不仅知道“通过了”，还知道在哪个环境、用什么数据、针对什么风险通过。

其次是可复现。dev 和 QA 每天更新 image，如果不记录精确 commit、配置、数据集和 Case 版本，昨天的失败和今天的通过可能根本不在同一上下文中。

最后是可失效。后续 PR 修改了同一条调用链、改变了环境依赖或测试判断标准，原有证据就可能失去效力。Agent 需要根据变化影响范围主动失效相关证据，并补充新的验证。

因此，main 的发布信心不是一个累计后只增不减的分数，而是一组持续更新的证据集合。

## 三、Agent 运筹的核心，是计算“证据缺口”

每种变化需要的验证强度不同，但决策过程可以统一表达：

    当前变更所需的质量证据
              -
    已经存在且仍然有效的质量证据
              =
           证据缺口

Agent 的测试计划不是从 Case 列表出发，而是从证据缺口出发。

这和医生选择检查项目有些相似。并不是每个人都做完全相同的一整套检查，而是根据症状、病史和风险先判断需要排除什么，再选择能够给出答案的检查。质量护栏相当于所有人都不能省略的基础检查，风险测试则因变更而异。

第一步是建立变更影响图。输入不仅包括 Git Diff，还包括调用关系、模块依赖、配置变化、历史缺陷、关联 Issue、近期 CI 失败和线上反馈。输出也不是一个简单的高、中、低风险分数，而是多维风险画像：

- 影响范围：局部路径、共享组件还是核心链路；
- 失败后果：结果错误、性能下降、资源泄漏还是服务不可用；
- 暴露条件：并发、数据规模、网络、缓存或特定部署环境；
- 新颖程度：成熟路径的小改动，还是缺少历史数据的新能力；
- 可检测性：普通功能测试能发现，还是需要故障注入和长时间运行。

第二步是将风险画像映射为证据要求。例如，高风险存储变更不仅需要功能正确性，还可能需要多云 S3、缓存一致性、异常恢复、尾延迟和资源生命周期证据。

第三步才是从 Case、数据集和环境中选择能够补齐这些证据的组合。

这个顺序非常关键。如果直接让 Agent 从海量 Case 中“猜应该跑什么”，它很容易依赖名称相似度；先定义风险与证据，再选择测试，决策才有稳定结构。

## 四、测试选择是有硬约束的运筹优化

我们拥有大量 Case 和数据集，但它们的价值并不相同。一个 Case 是否值得进入当前计划，至少与五个因素有关：

- 与当前风险的相关性；
- 历史缺陷发现能力；
- 相对其他 Case 的覆盖独特性；
- 执行稳定性；
- 时间、机器和环境成本。

可以把计划目标抽象为：

    最大化：
    风险覆盖 × 缺陷发现收益 × 覆盖独特性 × 证据时效

    最小化：
    执行时间 + 资源成本 + 重复覆盖 + Flaky 噪声

    约束：
    质量护栏、反馈 SLA、资源容量和必要环境覆盖

实际系统不必一开始就使用复杂模型。确定性规则可以负责质量底线，集合覆盖用于减少重复组合，优先级队列和背包模型用于资源预算，历史结果则用于校准 Case 价值。

这里必须区分硬约束和优化空间。

数据正确性、事务一致性、关键兼容性和已知高损失风险属于硬约束。Agent 不能因为资源不足或者历史失败率低而静默跳过。资源预算内如何选择更多高价值测试，才属于可以动态优化的空间。

为了证明动态计划没有牺牲质量，新策略需要先运行在 Shadow Mode，也就是“影子验证”：Agent 先给出自己会选择哪些测试，但暂时不控制真实门禁，后台继续与原有计划或全量测试对照。我们关注它错过了哪些失败、增加了哪些无效执行，以及对高风险场景的召回率。只有经过足够对照，动态计划才逐步参与真实门禁。

这比直接用“测试数量减少了多少”评价优化更可靠。减少执行不是目标，在相同或者更低成本下保持关键缺陷发现能力才是目标。

## 五、已有基础设施需要从“环境列表”变成“能力资源池”

我们在阿里云和腾讯云拥有固定 VM、S3 资源，有长期运行且每天更新 image 的 dev、QA 环境，也在上海 IDC 运行自己的私有 Cloud；同时积累了大量数据集和测试 Case。

如果这些资源仍然由不同任务各自申请、各自排队，它们只是一份环境清单。Agent 要进行运筹，首先需要把它们描述成统一的能力资源池。

dev 的特点是接近最新 main、启动反馈快；QA 适合更大范围回归、跨模块组合和长时间运行；阿里云、腾讯云提供真实的多云 VM、S3 和网络条件；IDC 私有 Cloud 覆盖私有化部署和基础设施差异。数据集也需要描述业务场景、规模、分布、更新成本和适用 Case。

每项任务声明所需能力，而不是直接指定某一台机器。调度 Agent 根据环境健康、当前 image、资源配额、排队时间和任务优先级选择执行位置。

它更像一个塔台，而不是坐在测试机旁不断按“开始”的机器人。塔台不负责驾驶每架飞机，但要知道哪项任务最紧急、需要哪条跑道、是否可以并行，以及什么时候必须等待或改道。

调度策略需要同时服务两种不同目标：

- PR 快速通道追求尽早给开发者提供可信反馈；
- main 持续验证追求覆盖广度、长时间稳定性和跨环境证据。

资源高峰时，调度器可以合并相同 commit 和计划的重复任务，为高风险修改预留或抢占资源，将长周期测试放入 QA 后台执行，并取消已经被新代码完全替代、且不再具有证据价值的任务。release 分支则拥有独立的资源预算，避免被 main 的并发流量淹没。

资源利用率并不是越高越好。持续 100% 占用意味着高风险任务到来时没有调度余量。Quality Engineering 追求的是按风险及时提供能力，而不是让所有机器永远忙碌。

## 六、一个 S3 读取变更如何走完整个闭环

以修改 S3 reader 或磁盘缓存路径的一类 PR 为例。

Diff 可能只涉及少量文件，但变更影响图会继续追踪对象存储读取、磁盘缓存、重试、并发控制和 reader 生命周期。结合历史 Issue，Agent 形成风险画像：

- 数据内容和 range read 是否保持正确；
- disk cache 命中、未命中和逐出后是否一致；
- 网络错误和重试是否重复消费 reader；
- 并发读取是否引入竞争或资源泄漏；
- S3、缓存和 reader 各阶段的尾延迟是否退化。

证据要求随之被拆成几层。

PR 阶段先执行基础读写、错误路径和资源关闭等快速护栏；变更相关的缓存逐出、并发和重试 Case 进入针对性计划；阿里云、腾讯云的 S3 资源验证真实对象存储行为；QA 承担大数据量、P99 和长时间运行；如果涉及私有化对象存储适配，再进入 IDC 环境。

假设 QA 发现 read-disk-cache P99 变慢，而 get-reader 仍然正常，失败归因 Agent 不会只给出“性能回归”。它会关联缓存命中率、磁盘队列、文件大小分布、淘汰行为、并发量以及同一时期的 S3 指标，帮助判断问题更可能来自磁盘读取、缓存抖动、资源竞争还是观测口径。

修复进入后，变更影响图重新计算。与修改路径无关且仍然新鲜的证据可以保留；受影响的缓存、并发和性能结果被失效并重新执行。最终形成的不是一串孤立 Job，而是一份能够说明“哪些风险已经被什么证据关闭”的质量记录。

这份记录随后跟随代码进入 main，并成为两周后 release 判断的一部分。

## 七、main 持续获得发布资格，release 才能轻

两周一发能否成立，不取决于 release 分支创建后团队跑得多快，而取决于此前两周 main 是否一直在构建发布信心。

换句话说，我们把 release 从一次“期末大考”改成了对日常成绩和最后增量的确认。真正决定发布速度的，是 main 在过去两周里有没有持续完成作业、纠正错误并保留可信记录。

在这套体系中，main 可以理解为持续接受发布资格验证的分支：

- PR 阶段拦截与当前变化直接相关的问题；
- 合入后由 dev 和 QA 补充跨模块、长周期证据；
- 多云和 IDC 持续补充环境维度；
- Issue、历史缺陷和线上反馈不断更新风险规则；
- 新变更主动失效已经过期的证据。

每两周准备拉 release 分支时，系统先回答一组 Readiness 问题：

- 所有高风险变更是否已经关闭证据缺口；
- 关键质量证据是否仍然新鲜；
- 是否存在未解决的严重回归；
- 目标部署环境是否覆盖；
- 性能和稳定性是否偏离基线；
- 最近的修复是否已经正确进入 main。

满足这些条件后，release 分支重点验证版本特有内容：升级与恢复、兼容性、安装交付、完整性能基线、已知问题以及分支后的增量修改。它继承 main 的有效证据，不盲目重跑所有内容，也不把 main 中尚未解释的风险带到发布阶段。

release 上发现的问题必须反向作用于 main。代码修复要同步，缺失场景要转化为 Case，错误选择要修正风险和调度规则。否则，release 只是解决了一个版本的问题，没有提升下一次发布能力。

快速发版的本质，是把一次集中式质量验收改造成持续式发布资格管理。

## 八、Case 不是越多越好，而要持续保持强度和正交性

Vibe Coding 同样可以快速生成大量测试。如果只看数量和覆盖率，测试资产会迅速膨胀，但不一定更能发现问题。

我们为 Case 建立多维画像：功能模块、调用路径、失败模式、数据规模、并发条件、部署环境、历史发现、运行成本和 Flaky 情况。Case 之间可以由此形成覆盖矩阵。

测试资产治理重点回答三个问题：

第一，强度是否足够。一个 Case 的断言是否真的能够识别错误，可以通过故障注入、Mutation Test、差分测试或历史缺陷回放验证。

第二，是否正交。如果多个昂贵 Case 长期覆盖同一风险，却没有带来独特发现，就应该合并、降频或者重新设计。

第三，是否贴近最新风险。一次严重 Issue 出现后，需要做 Test Gap Analysis：为什么没有发现，是缺少 Case、数据、环境、故障模型，还是计划没有选择已有 Case？对应结论必须进入下一版风险模型和测试计划。

Agent 可以持续计算 Case 的边际价值，但淘汰关键 Case 需要证据。先降低频率、进行 Shadow 对照，再决定是否退出关键路径，避免为了追求资源指标造成不可见的质量下降。

## 九、Agent 必须被治理，不能成为新的质量黑箱

Agent 会犯错：可能低估影响范围、被不完整历史数据误导，也可能为了缩短反馈而给出过于激进的计划。

因此，Agent 运筹需要一个独立于模型的治理面：

- 确定性规则定义不可绕过的质量护栏；
- 证据不足或模型低置信度时默认升级验证；
- 每次测试选择都能解释覆盖了什么、跳过了什么；
- 输入、规则、计划、执行环境和结果全程可审计；
- 高风险豁免和最终发布有明确责任人；
- Agent 版本和策略可以回放、对照与回滚。

人的角色也会发生变化。开发者需要说明变更意图和潜在影响；测试人员从重复执行转向风险建模、场景设计和资产治理；技术负责人制定质量底线、资源策略和发布标准；Agent 负责高频的信息处理、组合优化和执行协调。

Agent 不是质量责任的替代者，而是让质量责任在更高变化速度下仍然能够被履行。

## 十、如何证明这套体系真正有效

Quality Engineering 不能用“跑了多少 Case”或者“机器利用率多高”证明价值。最终结果必须同时覆盖质量、速度、资源和进化能力。

| 维度 | 核心指标 | 它回答的问题 |
| --- | --- | --- |
| 质量 | 高严重性缺陷逃逸、回归缺陷、首次发现阶段 | 问题是否被更早、更有效地发现 |
| 反馈 | PR 首次可信反馈时间、P95（95% 的 PR 能在此时间内获得反馈）、失败归因时间 | 研发是否真的获得更快反馈 |
| 发布 | main 健康度、release 稳定周期、紧急修复数量 | 高速迭代是否转化为可预测发布 |
| 资源 | 单位风险覆盖成本、排队时间、重复执行比例 | 有限资源是否投入了高价值验证 |
| 测试资产 | Flaky、覆盖独特性、历史缺陷检出能力 | Case 集合是否有效、稳定、正交 |
| Agent | 高风险召回、计划解释率、Shadow 漏检、人工推翻率 | Agent 决策是否可信并持续改善 |

这些指标必须联合判断。反馈变快但缺陷逃逸增加，不是成功；资源成本下降但高风险召回下降，也不是成功；Agent 自动化率提高但人工无法解释其决策，同样不是成功。

单日 40 多个 PR 的意义，也不是证明研发吞吐有多高。它更像一次容量检验：当变化突然增加时，系统能否保持反馈时延，能否把资源优先给真正高风险的修改，main 是否仍然健康，两周后的 release 是否仍然可预测。

## 十一、几个值得复用的经验

第一，不要从“有哪些测试”开始设计计划，要从“这次变化需要哪些证据”开始。Case 是满足证据要求的手段。

第二，不要把 release 当作质量开始收敛的时间点。release 能有多快，取决于 main 在整个周期中积累了多少仍然有效的发布信心。

第三，不要只优化测试执行。环境版本、数据集、日志指标、失败归因和证据失效同样决定结果是否可信。

第四，不要一开始就把 Agent 当成全自动决策者。先结构化数据和政策，再在 Shadow Mode 中验证选择质量，最后逐步扩大决策范围。

第五，不要用资源满载作为效率目标。质量系统必须为突发的高风险任务保留响应能力。

第六，不要把线上缺陷只转化成一个回归 Case。它还应该改变风险模型、测试组合、环境覆盖或质量门禁。

## 结语：Agent 带来的重要变化，是让质量决策可以规模化

七月那一天的 40 多个 PR，只是 Vibe Coding 时代研发变化加速的一个缩影。

真正的问题不是团队能不能生产更多代码，而是开发测试体系能否同样快速地理解这些变化，形成可信证据，并把风险控制在 main 和 release 之前。

MatrixOne 的 Quality Engineering 实践，最终建设的是一套 Agent 驱动的质量运筹系统：它连接代码、Issue、历史缺陷、测试资产、环境资源和发布政策，持续计算风险与证据缺口，在有限资源下选择最有价值的验证，再从每次执行和问题中修正下一轮决策。

当质量决策能够规模化以后，高速迭代与快速发版才不再彼此牺牲。main 每天都在更新自己的发布资格，release 分支只是对这份资格做最后确认。

两周一发的真正基础，不是发版前跑得更快，而是过去两周中的每一次变化，都得到了与风险相匹配、可以解释、可以复现的验证。
